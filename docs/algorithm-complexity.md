# 三方案检索逻辑、复杂度与时间口径

本文对应当前标签检索实现，不包含完整密码学协议或网络服务。
源码入口见 [PreFuzzDup](../PreFuzzDup/src/persistent_lookup.cpp)、
[SimLESS](../SimLESS/src/lookup_benchmark.cpp)、
[FuzzyDedup](../FuzzyDedup/src/lookup_benchmark.cpp)。

## 符号与目标

`N` 为参考标签数，`L=256` 为标签位数，`w` 为机器字位数，`s=t+1`。
阈值 `t` 是允许不同的位数，不是分段数；`t=4` 时分为 5 段。

| 方案 | 检索目标 | 持久化访问 |
| --- | --- | --- |
| PreFuzzDup | 返回所有距离不超过 t 的记录 | 分段倒排等值查找，再读取候选完整标签 |
| SimLESS | 求全局最小距离，再判断是否命中 | 读取全量标签 BLOB |
| FuzzyDedup | 找到首个距离不超过 t 的标签 | 按重量范围读取标签 BLOB |

## PreFuzzDup

标签按同一规则分成 `s` 段。若总距离不超过 `t`，至少一段完全相同。
服务端先查内存 Prefix Filter，仅对可能存在的段访问 SQLite。
倒排主键是 `(type, segment, value, record_id)`；段位置属于键的一部分，
所以 q1 只定位第 1 段相同的记录，不与其他位置比较。
SQLite 定位等值键后读取 posting，并非遍历所有段值。
汇总 posting、去重、读取完整标签计算距离后，返回排序后的结果。

设 `M=Ns`，实际倒排定位次数为 `G<=s`，读取 posting 数为 `P`，
去重后距离校验记录数为 `C`，最终返回数为 `R`。
固定标签长度与键长度下，采用期望常数时间的哈希去重，可概括为：

```text
查询：O(s + G log M + P + C(log N + L/w) + R log R)
建库：O(N log N + Ns log(Ns))
```

若将 L 作为变量，另计分段构造和段键处理的成本。倒排有 `Ns` 项，
每项存储约 `L/s` 位段值及记录标识，标签与段值合计为 O(NL) 位量级，
另有 O(Ns) 项管理开销。过滤器常驻内存，完整标签与倒排项持久化。
这些公式不是物理磁盘 I/O 次数；缓存、页大小、B-tree 扇出都会影响实测。
热门段值可能产生很长的 posting，不能保证任意数据下都是亚线性检索。

## SimLESS

每次读取全量标签块并扫描 N 个标签，时间为 `O(NL/w)`；没有因为已经
发现近邻而停止，因为输出包括全局最小距离。SQLite 只帮助取出标签块，
不减少逐标签距离比较数量。标签存储与全量 BLOB 的内存量级均为 `O(NL/8)`。

## FuzzyDedup

利用 `|weight(q)-weight(x)| <= Hamming(q,x)`，只读取重量位于
`[weight(q)-t, weight(q)+t]` 的桶。对桶内记录分三段累计距离，超过阈值
即停止该记录，找到首个符合阈值的记录则结束整个搜索。

设重量范围内实际物化的标签数为 B，实际检查的记录数为 E，E<=B；
查询包括桶键定位、`O(BL/8)` 字节读取/复制及最多 `O(EL/w)` 比较工作。
提前命中可以减少 E，却不一定减少已经读取的 BLOB 大小。最坏 B、E
均可达到 N。重量桶只有 L+1 种，桶内仍可能很大。

两个对比程序建库均保存全量块与重量块，标签空间为 O(NL/8)，带常数倍副本。
分桶准备按标签处理全部数据；实际建库还包含 BLOB 写入与数据库元数据操作。

## SQLite 与时间

SQLite 的有序树索引在 PreFuzzDup 中用于细粒度段键定位，在 FuzzyDedup
中用于较粗的重量桶定位；SimLESS 没有候选裁剪。性能差距主要取决于
索引选择性和各自输出目标，不能仅归因于 B-tree 与 B+ tree 的名称区别。

`latency_us` 是 C++ 查询函数的墙钟时间，包含其实际 SQLite 读取、候选处理
和距离计算，不包含正文标签生成、建库、网络或密码学协议。
`index_prepare_us` 是 PreFuzzDup 打开/建立持久化索引及重建内存过滤器的时间。
SQLite 应用页缓存约 1 MiB 不等于进程内存上限；返回的 BLOB 和 OS 页缓存另计。
本轮未清空 OS 页缓存，不能把结果当作冷机械盘性能或 4210 两机服务性能。
