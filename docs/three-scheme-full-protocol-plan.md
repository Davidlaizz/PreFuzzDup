# 三方案全量文本客户端与服务端实验规划

创建：2026-09-29；更新：2026-10-03。状态：规划草案，尚未实现或运行本轮实验。

## 1. 目标与范围

本机作为客户端，Xeon Silver 4110 机器作为服务端，继续使用 Enron 全量邮件文本。比较 PreFuzzDup、SimLESS、FuzzyDedup 在统一检索输出下的计算开销及最终复用效果，并观察第一候选失败后，后续候选是否能使复用成功。

本轮新增完整查询流程：正文预处理、256 位标签生成、候选检索、所有权证明、密文返回、客户端解密与内容相似确认、服务端绑定引用。首次入库的加密及无人选可用时的新文件上传单独统计。图片不纳入本轮。

本轮采用“全量参考标签 + 本轮查询相关密文”的存储模拟：服务端保留完整 413,921 条参考标签和检索索引，只为固定 5,000 条查询涉及的参考候选及实际新上传准备密文，不加倍存储整个参考资料。“5,000”是查询条数，不是必须生成的密文对象数，也不是可以截断全部候选的上限。

沿用现有密码学实现，不替换算法，也不把现有原型自测表达为已经完成三方案安全性或完整论文复现验证。所有权证明不等同于普通登录认证，各方案的证明机制分别保留。

## 2. 当前基础与需要补齐的内容

| 模块 | 当前情况 | 本轮工作 |
| --- | --- | --- |
| 两机检索交接 | 已完成 full 标签检索，有缓存和无 SQLite 缓存结果 | 保留旧结果，新增独立实验目录 |
| PreFuzzDup 检索 | persistent_lookup 返回全部候选 ID，按 ID 排序；完整协议按距离排序 | 统一结果结构与排序，支持两种模式 |
| SimLESS 检索 | 计算全局最小距离，当前结果不返回候选 ID 列表 | 保留记录映射，返回最近一条或全部候选 |
| FuzzyDedup 检索 | 重量筛选、分段距离提前终止、首个达标返回 | 最近一条也必须保证最小距离，全部模式须完整枚举 |
| PreFuzzDup 协议 | 有首次加密、模糊恢复、挑战签名验证、解密和引用绑定 | 拆分进程与消息，增加分阶段计时及最终确认 |
| SimLESS / FuzzyDedup 协议 | 有 CP-ABE/配对证明、OT/加解密测试入口 | 从测试输入接到真实正文，拆分角色与消息序列 |

因此，“另外两个方案都只返回最近一条”不适用于当前实现：FuzzyDedup 原本只保证首个匹配。改造后的模式需单独命名，旧基准不能直接当作新模式结果。

## 3. 查询集：5,000 条，近似占 20%

沿用全量 517,401 条数据的既有划分：参考库 413,921 条，查询池 103,480 条；不把正式查询重新放入参考库。统一正文提取规则：移除外层邮件头、CRLF 转 LF、去掉首尾空白，保留引用和签名，不做 MIME 解码。

用户确定：正式查询 5,000 条，其中近似查询 1,000 条、完全相同查询 200 条。为把此配额落实成可验证规则，建议继续使用阈值 4、5、6，并采用以下主实验分组。这里的 d_min 是查询标签与整个参考库的最小标签 Hamming 距离。

| 分组 | 数量 | 比例 | 主实验建议判定 |
| --- | ---: | ---: | --- |
| exact_ref | 200 | 4% | 参考库存在规范化正文 SHA-256 相同的记录，且根对正文一致 |
| near_ref | 1,000 | 20% | 无相同正文，且 1 <= d_min <= 4 |
| no_match_ref | 3,800 | 76% | d_min > 6 |

此配置使三个阈值下的标签命中数均为 1,200，即 24%；20% 专指非完全相同的近似标签查询，不包含那 200 条。最终证明或复用成功率不预设为 24%。
主实验不纳入 d_min=5/6 的边界查询，也不纳入“正文不同但标签距离为 0”的查询；分别统计其池规模，后续可做独立补充实验。这是为了维持同一查询集在三个阈值下的配额，不代表这些数据没有价值。

**合成近似查询设计（路线一）**：对真实 Enron 正文做“一个词替换/增删”会产生 20-80 的距离跳变，无法自然落入 1-4 的近邻带。因此合成 near_ref 采用“参考 tag 位翻转 + 占位正文”的方式：

- 从参考库随机选一条记录作为 base，取其 256 位 tag，随机翻转 1-4 个 bit 作为查询 tag。这保证 d_min 精确落在 1-4。
- 查询正文不反推自翻转后的 tag，而是取 base 的真实正文并做轻微词级编辑（保留签名/排版/大小写），作为该查询的“近似正文”。此正文仅用于后续加密/内容比对阶段，不影响检索阶段的 d_min。
- 检索阶段以翻转后的 tag 为准；内容相似确认阶段以编辑后的正文为准。两者分别统计，互不替代。

执行规则：
1. 对整个查询池进行精确标签距离分类，并记录正文相同与否；分类工具需独立全扫描抽取与小规模交叉测试，不能拿待评估检索器自身结果充当唯一真值。
2. 先报告各组可用数量。若 near_ref 不足 1,000，停止正式抽样并报告缺口；不重复凑数、不复制 ID、不通过直接翻转标签冒充真实邮件。
3. 如需补真实正文扰动样本，另列构造实验并记录来源，不能静默混入自然样本主实验。
4. 建议固定抽样种子 20260929，各组无放回抽样后固定查询顺序；正式性能测试之外另取验证集。
5. near_ref 是标签距离分组，不自动代表语义近似。解密后的独立内容相似确认另行记录。

这是控制配额实验，报告不得把整体命中率解释为 Enron 自然重复率。查询分类及抽样耗时不计入在线查询耗时。

### 3.1 5,000 条配置与配额联动

新协议交接工具使用独立 manifest，集中定义 reference_count=413921、query_pool_count=103480、benchmark_query_count=5000、group_counts={exact_ref:200, near_ref:1000, no_match_ref:3800}、thresholds=[4,5,6]、modes=[nearest,all]、repeat=3。客户端打包、服务端校验、运行循环和客户端分析均读取同一配置，不各自硬编码不同数量。

- 正式输入命名为 queries_bench_5000.csv 与 query_groups_bench_5000.csv；标签行数、分组行数、ID 集合和 manifest 必须一致，每个查询恰有一个分组。5,000 个 ID 不等于 5,000 种不同正文，不得预先去重查询来改变配额。
- 现有 tools/lookup-handoff/handoff.py 包含 BENCHMARK_QUERY_COUNT=1000、旧文件名和两组标签规则，不能直接用于新实验。新工具实现三组校验及配额衍生数量；旧工具和旧实验输入保留原样。
- 每个方案、模式、阈值有 5,000 × 3 = 15,000 条查询终端；每个方案每个模式共 45,000 条；每个方案两模式共 90,000 条；三方案合计 270,000 条。重复运行和候选尝试不计作新增查询。
- 验证集单独记为 verify_query_count，不占用 5,000 条正式配额；它所需的候选协议产物另列清单。任何配额、文件名、唯一键或结果数不符均报错，不能沿用旧实验的 9,000 行验收条件。

## 4. 统一检索与候选尝试口径

| 模式 | 检索输出 | 后续协议行为 |
| --- | --- | --- |
| nearest | 阈值内距离最小的一条，无匹配返回空 | 只尝试这一条，失败则不再选择第二条 |
| all | 阈值内全部候选，按距离升序，后再按确定 record_id 升序 | 按顺序逐条尝试，成功即停止；全部失败进入新上传路径 |

record_id 使用各方案一致的数据集 ID，不能用随机生成的协议内部 ID 决定同距离顺序。检索比较计入结果构造和排序，序列化另计；all 必须完整产生列表，不能以截断 top-k 冒充全部。

保留各方案检索机制：PreFuzzDup 使用 Prefix Filter 与分段倒排；SimLESS 使用全库扫描；FuzzyDedup 使用重量筛选与分段剪裁。FuzzyDedup 的 nearest 不能因遇到首个达标记录就结束，all 也不能遗漏候选。必要的算法改造和额外成本必须披露。

相同输入、阈值与模式下，三方案必须返回相同的候选 ID 和真实距离。随后分别运行本方案的证明与加解密；协议成功率不强制相同。若同一协议在两个检索模式下的成功率不同，才可量化“继续尝试候选”的收益。若三方案 all 列表一致，最终差异不能再归因于候选数量。

## 5. 完整业务流程与密钥职责

检索标签沿用现有 256 位文本 SimHash；它不是用于判定正文完全相同的 SHA-256。各协议内部密钥编排、域分离、KDF、随机数、访问策略及证明参数保持原实现，不因统一检索标签而统一密钥。

### 5.1 全量标签与按需协议产物

服务端初始化两类数据，避免把“已有标签”误认为“已存储完整密文”：

| 数据 | 覆盖范围 | 生成与存储规则 |
| --- | --- | --- |
| reference_tags 与完整索引 | 全部 413,921 条参考记录 | 保留 record_id、type、256 位 tag；不因密文未准备而删除标签或缩小索引 |
| 协议元数据和参考密文 | 5,000 条查询及验证集所需的参考候选 | 客户端读取对应真实正文，按方案生成 helper、公钥/策略、封装、密文，按记录去重准备 |
| query_tags | 本轮 5,000 条查询 | 请求数据，与参考标签表分开；不因上传查询而加入冻结参考库 |
| 新上传密文与引用 | 实际协议执行产生 | 写入当前轮次 overlay，记录复用关系，不回填冻结检索参考库 |

“模拟密文”指减少准备范围，实际使用的密文仍由原加密算法加密真实正文产生；不能用空文件、随机占位内容或预设解密成功代替。未涉及的参考记录允许为 tag_only 状态，相关记录必须为 protocol_ready，且具有证明和解密所需的完整公开产物。

本机已有标签先校验后复用；只为相关候选读取正文和初始化协议。模拟参考记录所有者和查询用户时隔离私密状态。服务端仅接收必要公开元数据与密文，各方案使用独立的协议产物空间。现有 PreFuzzDup 完整 records 表要求 helper、密钥封装等非空，因此实现时需将全量检索标签与稀疏协议记录分别管理，不能只向完整协议表插入部分记录后让它们代替全量检索库。

PreFuzzDup 查询用户需要通过候选 helper 和自己的内容恢复秘密材料，再解封装数据密钥；不能把参考所有者的数据密钥直接分发给所有查询用户。SimLESS 的授权属性和私钥、FuzzyDedup 的秘密材料也按原机制配置，准备成本单列。

### 5.2 需要准备哪些密文

固定参考集 R 和 5,000 条查询集 Q 后，在准备阶段计算相关候选集合：

```text
C_t(q) = {r 属于 R，且 Hamming(tag(q), tag(r)) <= t}
U_bench = 所有 q 属于 Q 的 C_6(q) 的并集
U_ready = U_bench 与独立验证集所需参考候选的并集
```

建议默认预先为 U_ready 生成各方案对应的参考密文和元数据。最大阈值 6 的候选并集覆盖阈值 4/5/6 的 nearest/all，使各模式使用同一逻辑参考快照。只生成候选涉及的文件，不生成其余参考密文；准备工作不计入查询耗时。预计算集合仅用于准备和验收，不供待测算法国工读取候选答案，也不能用“存在密文”代替全量索引搜索。

初始参考密文不等于查询文件的密文：例如 20 条查询都指向同一参考 record_id，该记录的完整协议产物每方案只准备一次；1 条查询有 10 个候选，all 模式可能需要 10 份参考协议产物。相似查询通过证明、解密和最终确认后才增加引用；失败才进入真实新上传路径。

因此候选并集可能小于、等于或大于 5,000。先输出实际 unique_candidate_records、reference_cipher_objects、reference_cipher_bytes 和预计新上传容量，再启动正式协议实验；不得为了迎合 5,000 份而截断候选。3,800 条 no_match_ref 在冻结参考库中均无候选，将触发新上传；其唯一正文数和实际对象数单独统计，不能把它们算成 3,800 份预存参考密文。

若 U_ready 超出实际磁盘预算，可在同一逻辑实验快照下按查询批次准备、运行、归档密文；单批必须覆盖该批完整候选，批间共用全量标签索引，缺失产物的准备成本在计时外完成并记录缓存预热影响。若无法提供某个被尝试候选的产物，本次为 artifact_missing 实验错误，不能记成证明失败或跳过后续宣布本轮有效。凡协议在证明前就需要密文的，例如 OT 路径，必须在证明开始前准备好，不能等验证成功才补密文。

### 5.3 去重、映射与容量统计

保留 query_id → ordered candidate record_id → scheme-specific protocol_record_id/cipher_object_id 的完整映射，每条密文清单记录文件路径、字节数、SHA-256 和公开元数据成员，密钥不进入清单。全部参考标签仍逐步记录保留，不能因正文相同合并记录而改变 candidate_count 或同距离顺序。

默认只复用同一方案内、同一完整协议记录的同一密文对象。相同正文的不同参考记录不能仅因正文 SHA 相同就共用密文：例如 PreFuzzDup 的 AAD 和密钥派生绑定记录及 nonce。未经原协议支持，不修改该绑定，不跨方案共用密文，也不按标签相似预先合并正文。真正的近似复用由运行中的协议成功及最终接受决定。

每个轮次单独报 N_ref（已准备参考对象数）、N_new（实际新上传对象数）、N_reused（接受复用的查询数）、N_unique_body（本地统计的唯一正文数）、cipher_bytes、metadata_bytes、index_bytes、peak_scratch_bytes 和 peak_RSS。密文数量与查询数量分别汇报；“相同相似所以一定少于 5,000”不是验收条件。

同一逻辑参考密文可以供不同模式、阈值及重复使用，证明状态必须隔离；新上传加密仍按每次真实执行计时，不能通过沿跨上次加密结果将加密耗时记零。不同轮次的新对象可以顺序归档后释放 scratch，不要求一次保存 270,000 次请求的全部密文副本。

本实验可报告“全量标签检索 + 所选查询的真实协议计算与按需密文读写”，不能声称测得全量密文常驻存储量、全量初始化加密成本或真实全量密文工作集的缓存性能。参考标签纯轻量仍为 413,921 × 32 = 13,245,472 字节；密文容量必须按实际文件求和，不能据查询数推算进程内缓存。

### 5.4 每次查询

| 步骤 | 客户端任务 | 服务端任务与消息 |
| --- | --- | --- |
| 1 | 提取正文、计算 tag，发送 query_id、用户标识、type、tag、模式和阈值 | 校验请求，执行候选检索与排序 |
| 2 | 接收候选列表和必要公开辅助信息 | 返回候选列表；对当前尝试候选生成新挑战或本方案初始消息 |
| 3 | 按原方案恢复密钥材料、生成签名或证明响应 | 校验响应；失败返回原状，不释放该候选密文 |
| 4 | 接收验证通过的候选密文及所需公开封装数据 | 验证成功后，读取并返回密文 |
| 5 | 按原方案解密，执行原有完整性检查，再比较新正文与解密正文 | 等待客户端最终判定 |
| 6 | 发送 accept/reject、query_id、record_id 和本轮会话标识 | 仅在证明成功且确认有效后绑定引用，并返回确认 |
| 7 | all 模式失败则尝试下一候选；nearest 失败或列表耗尽则新文件加密上传 | 新上传记录和计时分开保存，完成本轮查询 |

“如果相似则回传”定义为回传接受消息及记录标识，不回传明文或私钥。最终客户端相似检查是业务接受条件，不代表服务端所有权证明。相似内容复用可能返回不同正文，不能声称逐字节恢复了用户的新文件。

建议最终相似确认沿用已有独立五词片段 Jaccard 指标，暂定 Jaccard >= 0.5，先判正文完全相同；非相同且不足五词的正文保守拒绝相似复用。此阈值属于待校准的业务参数，不是语义真值或已验证的安全边界。记录分布并抽查边界样本；禁止只用相同 SimHash 阈值再次确认相似。

## 6. 分阶段计时与通信估算

所有实际计算使用所属机器的单调节时钟；不相量两台机器的墙上时间。客户端和服务端均记录每个尝试的 query_id、scheme、mode、threshold、repeat、candidate_rank 与状态。

| 计数字段 | 侧别 | 内容 |
| --- | --- | --- |
| input_read_us / preprocess_us / tag_us | 客户端 | 文件读取、正文处理、标签生成分别计时 |
| lookup_us | 服务端 | Filter/索引或扫描、距离计算、结果构造与排序 |
| challenge_us / proof_client_us / proof_verify_us | 服务端 / 客户端 / 服务端 | 挑战、签名或其他证明生成、验证；多轮证明逐轮记录 |
| key_recovery_us / decrypt_us / integrity_check_us | 客户端 | 秘密恢复与解封装、正文解密、原协议完整性验证 |
| similarity_check_us | 客户端 | 新正文与恢复正文的独立相似检查 |
| encrypt_us / wrap_us | 客户端 | 初始化或新上传的正文加密、密钥封装 |
| cipher_read_us / cipher_write_us / bind_us | 服务端 | 密文读写和最终引用绑定 |
| serialize_us / deserialize_us | 两侧分别记录 | 消息编码和解码 |

外层请求总时长与上述互斥阶段分别记录，嵌套计时不得重复相加。未执行阶段标 not_run；失败尝试、失败原因和已消耗通信均保留。标签生成不能因读取预计算 CSV 而记成真实生成耗时。

按用户要求统一通信环境。建议主场景 RTT=1 ms、有效带宽 B=1 Gbit/s，约作同一局域网的实验假设，不声明是普遍实测值。不給所有算法固定相同总通信时间，而给每条协议消息相同的链路参数：

```text
单条单向消息估算 = RTT / 2 + 8 * 消息字节数 / B
T_network_est = 串行消息估算之和
T_compute = 客户端计算时间 + 服务端计算时间
T_request_est = T_compute + 两侧文件 I/O 时间 + T_network_est
```

秒与微秒统一换算后汇总；计算时间包括消息编解码，但不包括已单独列出的文件 I/O。统计实际消息方向、次数、大小，包括候选列表、helper、挑战、证明、密文、确认和失败重试。协议有不同轮数，不能强行按相同轮数计费；OT 内部消息也计入。
主实验按单查询串行逻辑计算，离线打包只优化操作，不把多个查询合并为一次通信。
可用 RTT=0.5/5 ms 做模型敏感性分析，无需重跑离线学。通信估算不使用 sleep；git clone/push/pull 和人工等待不计入。
必须同时报告纯计算时间、通信估算和合计估算，合计不标为实测端到端时延。

## 7. 两机离线交接与运行控制

按照准备包、服务端候选挑战包、客户端证明包、服务端验证/密文包、客户端确认包、服务端回执包分批交接；每个消息记录 schema_version、run_id、输入摘要、query_id、record_id、轮次与唯一 message_id，并校验文件 SHA-256。重复导入不得重复消耗证明或绑定引用，乱序消息明确拒绝。

Git 继续传递代码、允许公开的标签、清单及脱敏报告。仓库库约束禁止提交正文、密钥、SQLite 和密文，不能把完整协议包直接照旧标签包 git add。建议运行期密文与协议产物通过受控离线文件通道交接，Git 只保存摘要；若必须全部通过 Git，需要另行确定允许保存实验密文的私有 artifact 仓库策略。未交接真实密文和证明消息前，不得声称完整两机协议已跑通。

现有 PreFuzzDup 挑战有效期为 120 秒，不适合人工 Git 往返。保持正常模式的现有规则，离线实验增加明确标识的会话时钟/有效期配置，保留单次使用及用户、候选、query_tag 绑定；测试没有期和重放搅局，不能简单删除过期校样。其余方案的交互证明也必须按真实轮次拆分。

缓存配置建议沿用最近无 SQLite 缓存实验：查询阶段 cache_size=0、mmap_size=0，OS page cache 保留。新增协议入口也需显式设置并读取确认，不能假设旧 CLI 参数自动适用。查询计时开始前建库完成，初始化时间独立报告。

每个模式、阈值、重复使用相同的逻辑初始参考快照，冻结检索参考库。查询产生的新上传和引用写入单独 overlay，避免后续查询因前序插入而改变候选。挑战、nonce 和会话状态每次重建，不复用旧证明。建议重复 3 次，固定种子轮换方案/模式执行顺序并记录，避免与固定顺序旧实验混淆。

## 8. 实施阶段与验收

1. **数据准备**：完成全查询池分类、配额可满足性检查、5,000 条抽样和独立真值；生成 U_ready、协议产物映射和容量清单。若配额不足或候选产物不完整先报告，正式协议实验不启动。
2. **统一检索**：增加 nearest/all；用小型可构造夹具和全量抽查验证集合、最小距离及同距离 ID 顺序；夹具不是新增 5w 实验。
3. **协议接入**：复用三方案加解密，拆分角色和消息；验证真实不同正文、错误秘密/属性、篡改、过期、重放，以及第一候选失败后第二候选成功的分支。不要把固定测试正文的自测计时冒充邮件实验。
4. **两机执行**：完成全量标签索引和相关参考密文初始化、实际产物交接和分阶段计时；按需初始化、重复查询、新文件上传分别统计。服务器安装原协议所需 PBC/GMP 等依赖，检索层可选依赖不代表完整协议不需要。
5. **汇总分析**：按方案、模式、阈值、分组报告 mean/median/p95/p99、候选数、尝试次数、证明通过率、解密成功率、最终复用率、通信字节与轮数、峰值 RSS 和磁盘占用。

验收要求：

- 查询 ID 唯一，参考/查询 ID 不重叠，各组为 200/1,000/3,800；同一查询集用于三方案和两模式；所有产物摘要可验证。
- 服务端参考标签始终为 413,921 条；密文数量按各方案实际协议对象报告，不强制等于 5,000。相关候选覆盖完整，重复查询指向同一参考对象时不重复初始化，缺失密文不得伪装成协议失败。
- 每个方案每个模式每个阈值每次重复都有 5,000 条终端记录；三个阈值、三次重复合计每模式 45,000 条，六个方案模式组合共 270,000 条。候选尝试明细单独保存，不充当查询数。
- nearest/all 检索结果分别独立真值一致；不强制不同协议的复用结果一致，不丢弃失败查询来提高成功率。
- 逐条查询报告 first_candidate_success、later_candidate_success、attempt_count、accepted_rank、final_status；all 的额外收益与额外证明、解密、通信成本一起呈现。
- 最终相似接受失败不建立引用；完整性或证明失败不得绕过；失败的新上传可被原协议正确恢复。
- 输出真实计算时间与通信模型结果，保存完整本地证据，汇总文档披露参数、缓存和运行顺序；原始私密产物不进入 Git。

建议新增实现位置为 tools/protocol-handoff/，数据写入 results-local/three-scheme-full-protocol/，服务端 SQLite/密文写入原生 scratch。各 C++ 项目继续独立构建，不引入相邻方案源码依赖。

## 9. 实施前需要固定的建议参数

本规划已确定：全量文本、5,000 查询、1,000 近似加 200 完全相同、nearest/all、两机分工、全量参考标签配合本轮相关密文按需准备、复用既有加解密、通信采用统一模型。

待实现阶段固定并写入 manifest 的建议项：阈值 4/5/6、近似组距离 1-4、其余组距离 >6、Jaccard 接受阈值 0.5、抽样种子 20260929、重复 3 次、RTT=1 ms 与 B=1 Gbit/s、离线挑战时钟策略，以及密文产物交接通道。查询池配额是否足够仍需实测，不能在规划阶段承诺最终复用率。
